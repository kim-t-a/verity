Verity

How the parts fit together

A user uploads documents, asks a question in plain language, and gets an answer that names the file and the place in it. Everything below exists to make those three things true at once: the answer is right, the citation is real, and an answer that does not exist is refused rather than invented.

The decision everything follows from

What changed when the machine got a language model

The engine this product is built on came from a challenge where no language model was available at answer time. The machine still had to produce a short literal answer, so the code grew a layer that guessed which sentence in the retrieved text was the answer: pattern-match the shapes an answer takes, score the candidates, pick one. That layer was the cleverest code in the repository and it was also the least honest, because a regex that picks the third-best sentence cannot tell you it guessed.

A language model makes that layer unnecessary. So it is deleted, not adapted — the pattern matcher, the candidate scorer, the extractor. What replaced it is a model that reads the retrieved passages and chooses, under a set of rules that stop it from choosing something it was never shown.

Deleted
Regex answer shapes, candidate scoring, span extraction. Code that had to guess because nothing could read.
Kept
PDF, DOCX, XLSX and OCR readers, chunking, normalisation, keyword search, reciprocal rank fusion. The parts that find text, not the parts that judge it.

This is the whole architecture in one sentence: the engine finds and ranks text; the model reads and decides; the backend checks that every citation points at something the model was actually shown. Each of the four processes below exists to keep one of those three jobs separate from the other two.

Architecture

Four processes, one shared database

Each runs in its own container under Docker Compose. They share no memory and no filesystem — the database is the only thing two of them have in common, which is what lets either be restarted without the other noticing.

browser

React / Vite

Uploads documents, asks questions, renders the answer with its citations, and can open the trace to show what was retrieved and which actions ran.

  • Documents screen
  • Chat screen
  • Citation panel
  • Trace panel

Never calls the model provider. The NVIDIA endpoint sends no CORS headers, so a browser cannot reach it — and the key must not be on the client anyway.

api

FastAPI

Owns the conversation. Rewrites follow-up questions, runs the agent loop, verifies citations, and holds the only copy of the provider key.

  • Session + turn history
  • Agent loop
  • Citation verification
  • Provider key

Never answers from remembered context. Every turn re-retrieves, so a citation always points at text fetched during that turn.

db

Postgres + pgvector

The only shared state. Holds chunks and their embeddings, the keyword index, the ingestion queue, and sessions.

  • chunks + vectors
  • tsvector index
  • Job queue
  • Sessions

Holds no files' original bytes as data — the file is stored once and served back for viewing.

worker

Python

Claims ingestion jobs and does the slow work: parse, chunk, embed, write rows. Imports the same verity.engine package the API does.

  • Parsing
  • Chunking
  • Batched embedding
  • Document status

Never lets one bad file abort the ingest. It catches per file, marks that document failed, and keeps going.

Who is allowed to talk to whom

  • browser → api Everything the user does goes through the API. This is the only edge the browser has.
  • api → provider The proxy is a security requirement, not a performance choice. It exists so the key never reaches the client.
  • api → db Reads chunks and vectors for retrieval; writes turns and summaries.
  • worker → db Claims a job with FOR UPDATE SKIP LOCKED. That is the whole queue — no Redis, no broker.
  • api ↛ worker No direct channel. The API enqueues a row and returns 202; the worker picks it up. Upload never blocks on parsing.
Path one

How a document becomes searchable

Runs in the worker. Nothing here involves a language model — this path is about turning a file into rows that carry their own provenance.

  1. Upload accepted

    The file is stored, a document row is created with status processing, and a job row is enqueued. The API returns 202 immediately.

    202 Acceptedstatus: processing

  2. Identify the format, then read it

    The type comes from the bytes, not just the extension. A reader turns the file into text plus spans — and each span remembers where it came from: a page number, a sheet and cell, a paragraph index, a region of an image.

    This is the step that makes citations possible later. Text without its location can be searched but never cited.

    PDF · DOCX · XLSX · CSV · text · imagespan → location

  3. Chunk on evidence, not on character count

    Split points follow the document's own structure — a heading, a table row, a paragraph — rather than a sliding window over characters. A chunk that starts mid-sentence is a chunk whose citation reads badly.

    retrieval unit

  4. Embed, in batches

    Chunks go to the embedding model in batches, with retry and partial-failure handling. Batching is not an optimisation here — Phase 0 measures the provider's real limits before this is written.

    NVIDIA NIM embeddingsretry

  5. Ready only when the last chunk lands

    A document flips to ready when every chunk has an embedding. If half the batch fails, the document stays visibly failed.

    A document that looks ready with holes in its index is the worst bug this system can have: it answers confidently from a corpus with pieces missing, and nothing on screen says so.

    ready = all chunks embeddedpartial ⇒ fail loudly

One bad file never costs you the corpus. A thousand-document upload does not fail because document 447 is an encrypted PDF. The failure is caught per file, recorded against that file, and the walk continues — so the user sees 999 documents ready and one named failure, instead of an error and no index.

Path two

How a question becomes a cited answer

Runs in the API. This is where a language model appears, and where almost every rule in the system is enforced.

  1. Retrieve before the model speaks

    Two retrievers run on the question: BM25 over the chunk text and its file path, and cosine similarity over the stored embeddings. Reciprocal rank fusion merges the rankings without pretending their scores are comparable. Empirically, keyword search carries identifiers — a clause number, an invoice id — while the vector side finds the same idea in different words.

    The vectors are stored in Postgres with pgvector. Today the API loads a workspace's chunks and ranks them in process; moving the ranking into SQL with an HNSW index is the spec's Phase 2, not something this page can claim is running.

    BM25, text + pathpgvector cosineRRF k = 60

  2. Show the model numbered extracts

    The retrieved chunks are numbered 1..N in the prompt, with their file and location attached. The conversation so far is passed alongside them. Those numbers are the only way the model can refer to evidence: anything it cites that was not in this listing is rejected in code.

    Nothing is injected silently. If a parent passage is added for context, it is shown and numbered too — the model never sees text it cannot cite.

    every extract has an idno hidden context

  3. The model chooses one of four actions

    The reply is one JSON object: search (retrieve again with a query the model wrote), answer (with the chunk numbers it rests on), clarification (one question that would unblock it), or refusal (with a reason). The loop runs at most five iterations. At the cap it must produce a best-effort answer, or refuse only when the evidence genuinely is not there.

    There is no deterministic ambiguity detector in the running code: the model is given the extracts and decides whether it needs a clarification. The spec's "top two within 15%" signal is still a design, and this page should not describe it as built.

    max 5 iterationsone JSON object, never prose parsing

  4. Verify every citation against what was actually shown

    When the model returns answer(text, citations), the backend checks each number against the chunks placed in front of the model during this turn. A citation to anything else does not survive.

    cited ⇒ was shown

  5. Return one of three shapes

    The response is a tagged union, so the frontend renders a decision rather than guessing at prose. An answer carries its citations; a clarification carries the question and any options; a refusal carries its reason and the passages it searched.

    answerclarificationrefusal

The four actions the model may choose

max 5 iterations per turn
search(query) Retrieve again with a query it wrote itself, then decide from a fresh numbered listing.
answer(text, citations) Ends the turn with an answer and the numbers of the extracts it rests on.
clarification(question, options?) Ends the turn by asking one question. Allowed, but never a way to avoid answering at the cap.
refusal(reason) Ends the turn with no answer, when the evidence genuinely is not there.
The rules

Five invariants, and what each one prevents

These are not style preferences. Each is a rule the spec states, a test asserts, and a well-meaning change is likely to break. The third column is the failure you would actually ship.

Rule What it says What breaks without it
I1 Retrieve at chunk level; the model may cite only chunks it was actually shown. Pulling in a larger parent for context is allowed — citing that parent is not. A citation that points at a passage the model never read. The quote on screen is not the text behind the link.
I2 Every chunk in the prompt carries an id the model may reference. No context is injected silently. An answer resting on text the user cannot see and cannot check.
I3 The clarification loop is capped. At the cap the system answers as well as it can, and refuses only when the evidence genuinely does not exist. A system that asks a third clarifying question instead of answering — a refusal dressed as diligence.
I4 Memory may shape the question. It may never be the evidence. Every turn re-retrieves. An answer about a document that was never retrieved this turn, cited to a file from four messages ago.
I5 A document is ready only when every chunk is embedded. Partial embedding fails loudly. Answers given confidently from an index with pieces missing, and no signal anywhere that it happened.
Conversation

Memory shapes the question, never the evidence

A conversation is useful because the second question can be shorter than the first. It becomes dangerous at exactly the same moment: the shorter the question, the more the system has to supply from memory, and supplied context is context nobody retrieved.

So memory is confined to one job. It may rewrite an ambiguous follow-up into a query that stands on its own. It may not answer anything. Every turn runs retrieval again, and every citation must point at a chunk fetched during that turn — which is invariant I4, and which is why the trace panel matters: the user can see the search that actually happened rather than the one implied by the conversation.

History is bounded by a token budget on recent turns, with older turns collapsed into a rolling summary stored on the session row. Conversations are per-session rather than per-person, because authentication is deferred — but the schema is shaped so adding a user_id later is an added column, not a redesign.

Build order

Six phases, each ending in something runnable

No phase starts before the one before it works. This is the rule that keeps the project from becoming a large unverified change.

  1. Phase 0

    Verify before building

    Docker Compose skeleton. Check the provider's real behaviour — which models the key reaches, how it signals rate limiting versus a billing failure, how large an embedding batch may be, and which input type the embedding models expect. Measure the 512-token ceiling on dense chunks.

    Blocked: needs an NVIDIA API key. Nothing model-shaped can be designed before this runs, because every number here is currently an assumption.

    Blocked
  2. Phase 1

    Extract the engine into a package

    The code you can read today. starter/app/ became an installable verity.engine with real imports instead of the flat-directory sys.path hack, challenge-only modules were deleted, and the test suite was pruned to assert only what still exists.

    Status: committed on feature/engine-extraction, and closed: the PDF flate cap is now measured on the decompressed output rather than the compressed input, and a CMap range that names code points beyond Unicode costs arithmetic instead of 16.7 million no-op steps. Both are pinned by regression tests. One defect remains deferred — the quadratic object table in _load_objects — pinned by a strict xfail and recorded as a prerequisite for Phase 3, since the worker is the first code that will accept an uploaded PDF.

    Complete
  3. Phase 2

    Storage

    Postgres schema and migrations. The in-memory chunk store is replaced by pgvector for the embeddings and a tsvector index for keyword search, with the existing fusion code now querying both instead of two Python lists.

    Next
  4. Phase 3

    Ingestion worker

    The job queue, the pipeline wired end to end, the batched embedding client with retry and partial-failure handling, and the document status lifecycle. This is where invariant I5 stops being a design and becomes a guarantee.

    Later
  5. Phase 4

    Agent loop and API

    The provider interface with a real implementation and a fake one, the four actions, the capped loop with structured output, citation verification, and the FastAPI routes. The fake provider is what lets every test of the loop run with no network and no key.

    Complete
  6. Phase 5

    Frontend

    Built: the documents list with its processing and failed states, the conversation and its answer sheet, the evidence rail, and the run-trace panel. The trace reports the queries, timings and fused ranks that actually ran; a turn whose trace was not stored says so rather than drawing a plausible one.

    Complete
  7. Phase 6

    Evaluation

    Labelled questions over real documents, and a harness that scores the system on them. If the spec's 15% ambiguity signal ships, this is where it stops being a starting value and becomes a tuned one.

    Later
Reading the code

Where each idea lives

Everything below exists on disk now. This is the half of the design that was reused rather than written — the parsers and ranking code carried over from the challenge engine.

verity/engine/ingestion/readers/ One file per format. Hand-written against the standard library — no parsing dependency, so the engine imports and tests with nothing installed. Each reader returns text plus the location of every span.
verity/engine/chunking.py Where a document is cut into retrievable units, following its own structure.
verity/engine/normalisation.py One normalisation function, used everywhere text is compared. Two would drift, and the drift would show up as a span that cannot be found.
verity/engine/retrieval/ Keyword search, vector search, and the fusion that merges their rankings. Phase 2 rewires these to query Postgres instead of lists.
verity/engine/embedding_provider.py The interface only. The challenge's local GPU backend is gone; Phase 3 supplies the provider behind it.
verity/engine/models.py The shared vocabulary — spans, read results, statuses — that every other module speaks in.
backend/tests/ The only test tree. Runnable with no network, no corpus and no key, because anything that calls a model sits behind an interface with a fake behind it.
legacy/ The challenge material, kept deliberately and marked not authoritative. It records why some parsing code looks the way it does, and its hostile corpus is still the best ingestion test data available.
